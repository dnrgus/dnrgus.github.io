개발

게임의 플레이 흐름부터 안전한 파일 처리, CTF 운영, 보안 테스트 자동화까지 직접 만든 결과물을 중심으로 돌아봅니다.

짧은 시간 안에 완성한 Magic Store

2026년 8월 20일부터 21일까지 진행된 게임잼에서 Unity 기반 마법 상점 게임 Magic Store의 프로그래머로 참여했습니다. 타이틀 화면에서 상점으로 이어지는 진행 흐름, 손님의 요구 조건에 맞는 주문 판정, UI와 게임 로직의 연결을 구현했습니다.

짧은 제작 기간에는 기능을 많이 추가하는 것보다 플레이 가능한 핵심 루프를 먼저 완성하는 일이 중요했습니다. 요구 조건을 경우의 수로 나누고, 화면과 판정 로직이 같은 상태를 바라보게 만드는 경험을 얻었습니다.

기능과 방어를 함께 설계한 Go 파일 공유 서비스

Go 표준 라이브러리만으로 웹과 curl에서 파일을 올리고 공유할 수 있는 서비스를 만들었습니다. 공유 링크, 기본 24시간 만료, Range 다운로드, 삭제 키를 구현했고 경로·확장자·MIME 검증을 함께 적용했습니다.

이 프로젝트의 핵심은 “업로드가 된다”에서 끝나지 않는 것이었습니다. 저장 용량과 요청 속도 제한, 임시 파일 정리, 보안 헤더, 비루트 컨테이너 같은 운영 조건까지 확인했습니다. 저장소에는 단위·통합 테스트, 실제 curl E2E, 방어 코드를 일부러 제거해 테스트가 실패하는지 보는 변이 검사 결과도 문서화했습니다.

CTF를 푸는 사람에서 환경을 만드는 사람으로

UNKNOWN Beginner CTF에서는 CTFd를 바탕으로 Web·Pwn·Reversing·Crypto·OSINT·Misc 문제를 담는 입문 플랫폼을 구성했습니다. MariaDB, Redis, Nginx, Docker Compose를 연결하고 Challenges와 Scoreboard 화면을 전용 테마로 정리했습니다.

CTF Solver Agent에서는 여러 LLM 솔버가 각자의 Docker 환경에서 문제를 풀고 관찰 결과를 공유하도록 기존 오픈소스 두 프로젝트를 결합했습니다. 정규식에 맞는 문자열을 곧바로 성공으로 처리하지 않고, 새 샌드박스에서 재현하거나 권위 있는 검증기가 수락했을 때만 종료하도록 검증 상태를 구분했습니다.

반복 가능한 보안 테스트 도구로 확장

LLM-BugBounty-Automation은 허가된 LLM·RAG·AI Agent·웹 서비스를 범위와 정책에 맞게 점검하는 자동화 프로젝트입니다. Scope와 Program Policy를 실행 게이트로 두고, 테스트 선택·실행·판정·재현·증거 정리·보고서 생성을 하나의 흐름으로 연결했습니다.

서로 다른 프로젝트였지만 공통된 방향은 같습니다. 입력을 처리하는 기능뿐 아니라 실패 조건, 범위, 재현 방법, 증거를 함께 설계해야 결과물을 다시 믿고 사용할 수 있다는 점입니다.

02 / 06

CTF/Wargame

메모리와 어셈블리 기초를 익히고, 워게임을 풀고, 참가자가 사용할 환경과 자동 풀이 도구까지 만든 과정을 정리했습니다.

시스템 기초를 글로 확인하기

Dreamhack 학습 기록은 Linux Memory Layout 2편과 x86-64 Assembly 5편으로 시작했습니다. Code·Data·BSS·Stack·Heap 영역을 구분하고, 레지스터와 피연산자, 주요 명령어를 정리한 뒤 퀴즈로 다시 확인했습니다.

용어를 한 번 읽는 것과 실제 코드의 변수가 어디에 놓이는지 설명하는 것은 달랐습니다. 답만 적기보다 “왜 그 세그먼트인가”와 “명령이 레지스터 상태를 어떻게 바꾸는가”를 문장으로 남긴 것이 다음 풀이의 기반이 됐습니다.

네 개의 워게임으로 도구를 익히기

  • Exercise: GDB — 중단점과 레지스터 값을 이용해 두 값을 확인했습니다.
  • addition-quiz — 반복되는 입출력을 자동화해 제한된 시간 안에 계산을 처리했습니다.
  • flag-shop — 여러 라운드의 상태와 선택 규칙을 분석하고 자동화했습니다.
  • shell_basic — seccomp 조건과 시스템 콜 제약을 확인하며 셸코드의 목적을 좁혔습니다.

이 네 글에서는 디버거, 입출력 자동화, 소스 분석, 제한 조건 확인이라는 서로 다른 접근을 경험했습니다. 이후에는 사용한 명령과 성공한 입력뿐 아니라 실패한 가설과 검증 기준도 함께 남기는 방향으로 기록 방식을 바꾸고 있습니다.

UNKNOWN Beginner CTF 제작

문제를 푸는 입장에서 한 단계 더 나아가, 초보자가 CTF에 진입할 수 있는 플랫폼을 만들었습니다. CTFd를 기반으로 여섯 카테고리의 문제 구조를 잡고, 전체 순위와 팀별 풀이 현황, First Blood를 볼 수 있는 Scoreboard를 구성했습니다.

문제 난이도만 낮춘다고 입문 환경이 되는 것은 아니었습니다. 카테고리 구분, 문제 설명, 실행 환경, 점수판, 테마가 한 흐름으로 이어져야 참가자가 길을 잃지 않는다는 점을 배웠습니다.

CTF Solver에서 검증을 설계하기

CTF Solver Agent는 여러 LLM 인스턴스가 서로 관찰 내용을 공유하면서 문제를 풀도록 만든 도구입니다. 각 솔버를 Docker로 격리하고, 반복 호출과 비용·시간을 제한하며, 후보 플래그와 검증된 플래그를 분리했습니다.

이 작업을 통해 CTF 자동화의 핵심이 “그럴듯한 문자열을 찾는 것”이 아니라는 점을 분명히 했습니다. 새 환경에서 풀이 스크립트가 같은 결과를 내거나 공식 검증기가 수락해야 비로소 해결로 기록하는 구조가 필요했습니다.

Bug Bounty

알려진 취약점을 이해하고 재현하는 활동과 실제 버그바운티 성과를 구분하면서, 책임 있는 테스트를 위한 도구를 만들었습니다.

공개 CVE를 구조적으로 읽기

React Server Components의 역직렬화 문제인 React2Shell(CVE-2025-55182)과 Windows Notepad 마크다운 렌더링의 CVE-2026-20841을 정리했습니다. 취약한 기능, 공격에 필요한 조건, 영향 범위, 완화 방법을 나누어 기록했습니다.

이 활동은 새로운 취약점을 최초 발견한 것이 아니라 공개된 CVE를 분석한 것입니다. “어디가 위험하다”는 결론보다 입력이 어떤 경로를 거쳐 위험한 동작으로 이어지는지 설명하는 연습에 초점을 맞췄습니다.

Fuzzing-101으로 크래시를 재현하기

AFL++로 Xpdf 3.02를 퍼징해 무한 재귀와 스택 고갈로 이어지는 CVE-2019-13288을 재현했습니다. 이어서 libexif 0.6.14를 대상으로 조작된 EXIF 입력이 힙 버퍼 오버플로와 범위 밖 읽기를 유발하는 CVE-2009-3895, CVE-2012-2836을 확인했습니다.

퍼징 환경 구성, 계측 빌드, 크래시 입력 확보, GDB 분석을 한 흐름으로 경험했습니다. 이미 알려진 취약점이더라도 크래시가 발생했다는 사실과 원인을 설명할 수 있다는 것은 다른 단계였습니다.

Scope first 자동화 프로젝트

LLM-BugBounty-Automation은 허가된 LLM·RAG·AI Agent·웹 기반 AI 서비스를 반복 가능하게 점검하기 위한 프로젝트입니다. 실행 전에 대상 범위와 프로그램 정책을 확인하고, 허용되지 않은 도메인·기법·요청량은 차단하는 구조를 우선했습니다.

테스트 결과는 실행 로그, 판정, Finding, Evidence, 재현 정보, 보고서로 이어집니다. 민감한 값은 삭제하거나 가리고, 한 번 나온 결과는 반복 시도와 negative control을 통해 다시 확인하도록 설계했습니다. 도구를 많이 실행하는 것보다 재현 가능한 근거를 남기는 것이 목표였습니다.

현재 위치를 정확히 적기

2026년 11월 현재 공개된 T-blog와 GitHub에서는 실제 버그바운티 프로그램에 제출해 접수·채택·보상받은 기록을 확인할 수 없습니다. 따라서 지금까지의 활동은 취약점 분석·재현과 테스트 자동화 기반 구축으로 표현하는 것이 정확합니다.

다음 단계는 허가된 프로그램 또는 의도적으로 취약하게 만든 로컬 환경에서 수동 검증을 병행하고, 정책 확인부터 재현 절차와 영향 분석까지 갖춘 모의 보고서를 축적하는 것입니다.

기록 방식의 변화

초기 Git 시리즈는 명령의 의미와 원격 저장소 흐름을 단계별로 익히는 학습 노트였습니다. Dreamhack 글에서는 개념을 설명한 뒤 퀴즈에 답했고, 워게임 글에서는 제공 파일과 코드를 살펴본 뒤 풀이를 이어갔습니다.

퍼징과 CVE 분석으로 넘어오면서 글의 구조도 달라졌습니다. TL;DR, 실습 대상과 환경, 원인, 재현 과정, 영향과 완화 방법을 나누기 시작했습니다. Go 파일 공유 서비스 글에서는 구현 기능뿐 아니라 위협 모델, 테스트 결과, 알려진 한계까지 함께 설명했습니다.

README를 실행 가능한 문서로 만들기

GitHub의 프로젝트 문서는 소개만 하는 데서 끝내지 않았습니다. 필요한 환경, 실행 명령, 디렉터리 구조, 보안 기준, 테스트 방법, 제한 사항을 README에 담았습니다. UNKNOWN Beginner CTF는 Docker Compose 실행 절차와 카테고리·점수판 기능을, CTF Solver는 브랜치 차이와 플래그 검증 상태를 설명합니다.

문서가 좋아야 새로운 사람이 같은 결과를 재현할 수 있고, 미래의 나도 왜 그런 선택을 했는지 다시 이해할 수 있다는 점을 배웠습니다.

두 블로그의 역할을 나누기

앞으로 각 글에는 작성일, 확인한 환경, 원문과 참고 자료, 직접 확인한 사실, 남은 한계를 일정한 순서로 표시할 계획입니다. 글의 수보다 근거를 다시 찾을 수 있는 구조가 더 중요하기 때문입니다.

논문/컨퍼런스

암호부터 물리계층, SecOps, AI Agent, Web3까지 이어진 세미나를 정리하고 ARM PAC 분석으로 관심 분야를 구체화했습니다.

암호와 시스템 보안의 연결

하계 보안 세미나 1강부터 3강까지는 암호가 어떤 가정 위에 서 있는지, 양자 컴퓨팅이 기존 공개키 암호에 어떤 영향을 주는지, SIS·LWE 문제에서 Kyber와 ML-KEM·ML-DSA가 어떻게 이어지는지를 정리했습니다.

4강부터 6강까지는 자동차 보안, 임베디드·자동차 시큐어 코딩 표준, 국가 보안적합성 검증 체계를 다뤘습니다. 알고리즘이 안전해도 실제 제품의 코드와 개발 절차, 검증 체계가 함께 받쳐주지 않으면 보안이 완성되지 않는다는 흐름을 확인했습니다.

통신과 보안 운영으로 범위 넓히기

7강과 8강에서는 무선 채널 특성을 이용하는 물리계층 보안과 제한된 전력 안에서 비밀 전송률을 높이는 최적화 문제를 공부했습니다. 9강과 10강에서는 SIEM·SOAR·EDR·XDR·CTI, Event와 Alert, 오탐과 미탐, 사고 대응 흐름을 정리했습니다.

11강과 12강은 도구를 호출해 행동하는 AI Agent의 보안 문제와 중앙기관 없이 거래를 검증하는 Web3·블록체인 구조를 다뤘습니다. 서로 다른 주제처럼 보였지만 신뢰 경계, 관찰 가능한 증거, 실패 시 대응이라는 공통 질문으로 연결할 수 있었습니다.

ARM PAC 보호기법 분석

별도의 분석 글에서는 ARMv8.3-A의 Pointer Authentication을 살펴봤습니다. 반환 주소나 함수 포인터에 인증 코드를 결합해 메모리 손상 공격으로 포인터가 바뀌었는지 확인하고, ROP·JOP 같은 제어 흐름 탈취를 어렵게 만드는 원리를 정리했습니다.

기존의 DEP/NX, ASLR, Stack Canary와 비교하며 PAC가 무엇을 보완하는지, 어떤 위협 모델을 전제로 하는지 나누어 설명했습니다. 보호기법을 이름으로 외우기보다 공격자가 가진 능력과 방어가 보장하는 범위를 함께 보는 연습이 됐습니다.

세미나 정리와 논문 리뷰는 다르다

현재 공개 기록에서 확인되는 것은 세미나 12강의 학습 노트와 기술 분석 글입니다. 직접 작성한 논문, 학술대회 발표, 특정 논문의 실험을 재현한 정식 리뷰는 아직 확인되지 않습니다.

따라서 이 활동의 성과는 폭넓은 연구 주제를 탐색하고 질문의 지도를 만든 것입니다. 다음에는 관심 분야를 ARM 시스템 보안과 AI Agent 보안으로 좁혀, 논문의 문제·방법·실험·한계를 같은 형식으로 비교하고 공개 코드가 있는 연구는 재현 결과까지 남길 계획입니다.

공모전/자격증

정해진 시간 안에 팀의 결과물을 완성한 경험과 참가자를 위한 대회형 환경을 만든 경험을 역할 중심으로 정리했습니다.

Magic Store 게임잼 참여

2026년 8월 20일부터 21일까지 Unity 기반 마법 상점 게임 제작에 프로그래머로 참여했습니다. 타이틀·상점 UI, 게임 진행에 필요한 백엔드 로직, 손님 요구 조건에 따른 주문 판정, 실제 플레이 흐름을 구현했습니다.

게임잼처럼 시간이 짧은 환경에서는 모든 아이디어를 구현할 수 없습니다. 팀이 합의한 핵심 경험을 먼저 정의하고, 화면이 연결되는 최소 흐름을 만든 뒤 판정 규칙과 예외를 보완하는 순서가 효과적이었습니다.

UNKNOWN Beginner CTF 제작

UNKNOWN Beginner CTF는 처음 CTF를 접하는 사람도 도전할 수 있도록 문제와 플랫폼을 함께 준비한 프로젝트입니다. 여섯 카테고리와 점수판, 팀별 상세 현황, First Blood 표시, 전용 다크 테마를 구성했습니다.

이 활동에서는 참가자의 입장을 생각해야 했습니다. 문제 자체뿐 아니라 실행 안내, 카테고리 구분, 풀이 현황, 서비스 기동과 복구가 모두 대회 경험을 만듭니다. 기능 개발과 운영 준비가 분리되지 않는다는 점을 배웠습니다.

결과를 부풀리지 않기

공개 저장소에서는 두 프로젝트의 제작 내용과 맡은 역할을 확인할 수 있습니다. 그러나 게임잼의 수상 여부나 UNKNOWN Beginner CTF의 실제 개최 결과·참가자 수·순위에 관한 공개 근거는 확인되지 않습니다. 따라서 여기서는 참여와 제작 경험만 성과로 기록했습니다.

또한 현재 공개 자료에는 취득한 자격증이나 응시 결과가 없습니다. 자격증 카테고리가 비어 있다는 사실도 현재 상태의 일부입니다.

다음 도전에서 남길 것

다음 공모전이나 대회에서는 시작할 때부터 목표, 기간, 팀 구성, 내 역할, 제출물, 피드백, 최종 결과를 한 문서에 기록할 계획입니다. 자격증은 이름부터 정하기보다 앞으로 집중할 보안 분야에 필요한 역량을 먼저 고르고, 공식 출제 범위와 실습 계획을 연결하겠습니다.

참여했다는 한 줄보다 어떤 제약에서 무엇을 맡았고, 결과물에 어떤 변화를 만들었는지를 설명할 수 있어야 다음 기회에도 경험이 이어집니다.
