기초 학습에서 CTF 플랫폼 제작까지

메모리와 어셈블리 기초를 익히고, 워게임을 풀고, 참가자가 사용할 환경과 자동 풀이 도구까지 만든 과정을 정리했습니다.

1. 시스템 기초를 글로 확인하기

Dreamhack 학습 기록은 Linux Memory Layout 2편과 x86-64 Assembly 5편으로 시작했습니다. Code·Data·BSS·Stack·Heap 영역을 구분하고, 레지스터와 피연산자, 주요 명령어를 정리한 뒤 퀴즈로 다시 확인했습니다.

용어를 한 번 읽는 것과 실제 코드의 변수가 어디에 놓이는지 설명하는 것은 달랐습니다. 답만 적기보다 “왜 그 세그먼트인가”와 “명령이 레지스터 상태를 어떻게 바꾸는가”를 문장으로 남긴 것이 다음 풀이의 기반이 됐습니다.

2. 네 개의 워게임으로 도구를 익히기

  • Exercise: GDB — 중단점과 레지스터 값을 이용해 두 값을 확인했습니다.
  • addition-quiz — 반복되는 입출력을 자동화해 제한된 시간 안에 계산을 처리했습니다.
  • flag-shop — 여러 라운드의 상태와 선택 규칙을 분석하고 자동화했습니다.
  • shell_basic — seccomp 조건과 시스템 콜 제약을 확인하며 셸코드의 목적을 좁혔습니다.

이 네 글에서는 디버거, 입출력 자동화, 소스 분석, 제한 조건 확인이라는 서로 다른 접근을 경험했습니다. 이후에는 사용한 명령과 성공한 입력뿐 아니라 실패한 가설과 검증 기준도 함께 남기는 방향으로 기록 방식을 바꾸고 있습니다.

3. UNKNOWN Beginner CTF 제작

문제를 푸는 입장에서 한 단계 더 나아가, 초보자가 CTF에 진입할 수 있는 플랫폼을 만들었습니다. CTFd를 기반으로 여섯 카테고리의 문제 구조를 잡고, 전체 순위와 팀별 풀이 현황, First Blood를 볼 수 있는 Scoreboard를 구성했습니다.

문제 난이도만 낮춘다고 입문 환경이 되는 것은 아니었습니다. 카테고리 구분, 문제 설명, 실행 환경, 점수판, 테마가 한 흐름으로 이어져야 참가자가 길을 잃지 않는다는 점을 배웠습니다.

4. CTF Solver에서 검증을 설계하기

CTF Solver Agent는 여러 LLM 인스턴스가 서로 관찰 내용을 공유하면서 문제를 풀도록 만든 도구입니다. 각 솔버를 Docker로 격리하고, 반복 호출과 비용·시간을 제한하며, 후보 플래그와 검증된 플래그를 분리했습니다.

이 작업을 통해 CTF 자동화의 핵심이 “그럴듯한 문자열을 찾는 것”이 아니라는 점을 분명히 했습니다. 새 환경에서 풀이 스크립트가 같은 결과를 내거나 공식 검증기가 수락해야 비로소 해결로 기록하는 구조가 필요했습니다.
