넓게 시도한 다음, 깊이를 증명하는 방법

많이 시도한 2026년의 장점은 살리고, 공개 결과물에서 드러난 빈틈은 측정 가능한 다음 행동으로 바꿉니다.

현재까지 확인한 강점

개발과 보안 학습을 따로 두지 않고, 파일 업로드 검증·CTF 환경·LLM 보안 테스트처럼 직접 구현하는 프로젝트로 연결했습니다. T-blog에는 36개의 학습·실습 글이 있고, GitHub에는 Unity, Go, Python, CTFd를 활용한 6개 공개 저장소가 있습니다.

특히 최근 프로젝트는 범위, 정책, 테스트, 재현, 한계를 문서에 포함합니다. 단순히 작동하는 데서 멈추지 않고 결과를 믿을 수 있는 조건을 고민하기 시작한 점은 분명한 성장입니다.

부족했던 부분

  1. 넓이에 비해 깊이를 보여주는 대표 결과물이 부족합니다. 관심 분야와 프로젝트는 많지만, 한 문제를 오래 추적한 실험 보고서나 안정적으로 운영되는 배포 사례는 적습니다.
  2. 버그바운티의 실제 제보 과정이 비어 있습니다. CVE 재현과 자동화 도구는 있지만, 허가된 프로그램에서 수동으로 검증하고 제출·트리아지까지 경험한 공개 기록은 없습니다.
  3. 세미나 노트가 논문 재현으로 이어지지 않았습니다. 12개 주제를 폭넓게 정리했지만 논문의 가설, 데이터, 비교 기준, 실험 결과를 직접 다시 확인한 글은 없습니다.
  4. CTF와 공모전 결과를 설명할 지표가 부족합니다. 워게임 풀이와 제작 저장소는 있으나 실제 대회의 문제 수, 역할별 기여, 참가 결과, 피드백을 한곳에서 확인하기 어렵습니다.
  5. 자격증 활동은 아직 근거가 없습니다. 취득·응시 기록뿐 아니라 어떤 역량을 위해 어떤 자격을 선택할지에 대한 계획도 공개되어 있지 않습니다.
  6. 문서의 기준이 프로젝트마다 다릅니다. 좋은 README가 있는 저장소도 있지만 모든 프로젝트에 설치, 테스트, 데모, 제한 사항, 릴리스가 같은 수준으로 갖춰진 것은 아닙니다.

첫 30일 — 정리와 대표작 선택

  • 6개 저장소에 목적·역할·실행·테스트·한계·다음 과제 항목이 있는지 점검표를 만듭니다.
  • 대표작을 Go 파일 공유 서비스와 LLM Bug Bounty Automation 두 개로 좁히고, 처음 보는 사람이 따라 하는 설치 검증을 수행합니다.
  • CTF 글 11편에 환경, 핵심 원리, 재현 절차, 실패한 가설, 배운 점이 있는지 다시 확인합니다.
  • 관심 논문 목록을 ARM 시스템 보안 3편, AI Agent 보안 3편으로 제한하고 선택 이유를 적습니다.

60일 계획: 재현 가능한 깊이

  • 선정한 논문 1편의 공개 코드와 실험 환경을 재현하고, 원 논문의 수치와 다른 결과가 나온 이유까지 기록합니다.
  • 의도적으로 취약하게 만든 로컬 서비스나 명시적으로 허가된 범위에서 모의 버그바운티 보고서 3개를 작성합니다.
  • UNKNOWN Beginner CTF 문제 중 한 카테고리를 선택해 문제 의도, 배포, 공식 풀이, 검증 스크립트를 한 묶음으로 공개합니다.
  • 대표 프로젝트에 버전 태그와 변경 기록을 추가하고, 자동 테스트 결과가 README의 주장과 일치하는지 확인합니다.

90일 계획: 외부 결과

  • CTF 또는 개발 공모전 한 곳에 참여하고 기간, 팀 역할, 제출물, 결과, 피드백을 하나의 회고로 남깁니다.
  • 버그바운티는 프로그램 정책을 먼저 기록한 뒤 범위 내에서 수동 검증을 진행합니다. 유효한 발견이 없더라도 테스트 범위와 배운 점을 남깁니다.
  • 자격증은 진로와 연결되는 한 개만 선택합니다. 공식 출제 범위와 현재 프로젝트 경험을 비교한 뒤 학습 여부를 결정합니다.
  • 이 페이지를 다시 열어 완료·미완료·중단 항목과 그 이유를 업데이트합니다.

매달 확인할 기준

  • 재현 가능한 심화 기술 글 2편
  • 독립된 환경에서 다시 통과한 프로젝트 검증 1회
  • 원문·실험·한계가 연결된 논문 리뷰 또는 취약점 보고서 1편
  • 새 활동보다 기존 결과물의 미해결 항목을 닫은 비율

수치를 채우기 위해 얕은 글을 늘리는 것은 이 계획의 목적이 아닙니다. 목표를 놓쳤다면 무엇이 막혔는지와 다음에 바꿀 조건을 함께 기록하겠습니다.
