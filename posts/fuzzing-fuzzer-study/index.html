퍼징 입문: 개념부터 AFL++, Jackalope, libFuzzer까지

퍼징이 무엇인지, 종류가 어떻게 나뉘는지, 퍼저마다 무엇이 다른지 공부하고 정리했다. 작은 C 예제 하나로 시드, 코퍼스, 커버리지, 오류 탐지기를 차례로 설명하고, 마지막에는 크래시를 찾은 뒤 확인할 순서까지 다룬다.

이 글에서 다루는 것

미션은 퍼징이 무엇인지 공부하고 여러 퍼저를 비교하는 것이었다. 참고한 자료는 AFL++, Jackalope, google/fuzzing 저장소다. 이 글은 직접 정리한 학습 노트이고, 퍼저를 돌려 CVE를 재현한 기록은 Fuzzing-101 실습 기록에 따로 적었다.

퍼징을 이해하려면 세 가지를 같이 봐야 한다. 어떤 입력을 만드는가, 그 입력을 어디에 넣는가, 무엇을 오류로 판단하는가이다. 글도 이 순서로 따라간다.

1. 퍼징이란

퍼징은 다양한 입력을 자동으로 만들어 프로그램에 반복해서 넣고, 실행 중에 문제가 생기는지 검사하는 테스트 방법이다. 파일을 읽는 프로그램이라면 정상 파일, 빈 파일, 일부가 잘린 파일, 길이 정보가 틀린 파일, 특정 데이터가 매우 많이 반복되는 파일을 모두 넣어 봐야 한다. 사람이 이런 경우를 하나씩 떠올려 실행하기에는 경우의 수가 너무 많다. 그래서 입력 생성과 반복 실행을 자동화한다.

1.1 코드로 이해하기

아래는 LAB으로 시작하는 레코드를 읽는 함수다. 4번째 바이트가 데이터 길이이다.

void parse_record(const unsigned char *data, size_t size)
{
    if (size < 4)       return;
    if (data[0] != 'L') return;
    if (data[1] != 'A') return;
    if (data[2] != 'B') return;

    size_t n = data[3];
    if (n > size - 4)   return;   // 입력 안에 n바이트가 있는지만 확인

    char buf[16];
    memcpy(buf, data + 4, n);     // n이 16보다 커도 막지 않음
    process(buf, n);
}

코드는 순서대로 입력이 4바이트 이상인지, 처음 세 글자가 LAB인지 확인하고, 네 번째 바이트를 길이로 읽은 뒤, 입력에 그만큼의 데이터가 있는지 확인하고, buf로 복사한다. 문제는 마지막 검사가 입력 크기만 보고 목적지 버퍼 buf[16]의 크기는 보지 않는다는 점이다.

b"LAB" + b"\x04" + b"ABCD"        # 정상: 길이 4
b"LAB" + b"\x11" + b"A" * 17      # 길이 17 > 16 → 스택 버퍼 오버플로

\x04는 숫자 4를, \x11은 숫자 17을 나타내는 한 바이트다. 17바이트짜리 입력은 크기 검사를 통과하지만 16바이트 버퍼에는 들어가지 않는다.

이 예제를 AddressSanitizer를 켜고 직접 빌드해 두 입력을 넣어 보았다. 정상 입력은 그대로 끝났고, 두 번째 입력은 memcpy에서 stack-buffer-overflow(WRITE of size 17)로 멈췄다. ASan이 없으면 같은 입력이 조용히 지나갈 수도 있는데, 이 이야기는 2장에서 다시 한다.

1.2 아무 값이나 넣으면 찾을 수 있을까

가능성은 있지만 효율이 떨어진다. 무작위 입력의 첫 바이트가 L일 확률은 1/256이고, 세 글자를 모두 맞출 확률은 약 1/16,777,216이다. 대부분의 입력은 data[0] != 'L'에서 바로 끝난다. 그래서 시드와 코퍼스라는 개념을 쓴다.

  • 시드(seed): 퍼징을 시작할 때 주는 입력이다. 앞의 예라면 정상 입력 b"LAB" + b"\x04" + b"ABCD"가 시드가 된다.
  • 코퍼스(corpus): 입력을 모아 둔 집합이다. 처음 준비한 시드뿐 아니라, 퍼징 도중 쓸모 있다고 판단해 보관한 입력도 들어간다.

퍼저는 기존 입력의 특정 바이트를 바꾸고, 일부를 지우고, 데이터를 덧붙이고, 비트를 뒤집고, 서로 다른 입력의 일부를 섞는다. 이를 변이 기반 퍼징(mutation-based fuzzing)이라고 한다.

1.3 어떤 입력이 쓸모 있는지 어떻게 알까

대표적인 기준이 커버리지(coverage), 즉 이번 입력으로 프로그램의 어느 부분이 실행됐는지에 대한 정보다. 위 코드에서는 입력에 따라 실행이 이렇게 갈린다.

입력어디까지 실행되는가
xyz…첫 번째 문자 검사에서 끝난다
Lyz…첫 검사를 통과하고 두 번째에서 끝난다
LAz…두 검사를 통과하고 세 번째에서 끝난다
LAB…헤더 검사를 통과하고 내부 처리로 들어간다

이 차이를 관측할 수 있으면, 새로운 실행 흐름을 만든 입력을 보관했다가 다시 변형할 수 있다. 그래서 L, LA, LAB을 한 글자씩 맞춰 가게 된다. AFL++의 탐색 흐름은 다음과 같다.

  1. 코퍼스에서 입력을 고른다.
  2. 입력을 변형한다.
  3. 프로그램을 실행한다.
  4. 새로운 실행 특징이 나타났는지 확인한다.
  5. 유용한 입력을 코퍼스에 추가한다.
  6. 반복한다.

다만 실제로 L, LA, LAB 순서로 맞춰 간다고 단정하면 안 된다. 계측 방식에 따라 달라진다. 퍼저는 실행 피드백으로 탐색을 개선할 뿐이고, 코드의 의미를 이해해서 취약한 입력을 계산하는 것이 아니다.

AFL++가 하는 일예
입력 변형정상 파일의 길이 값을 바꾸거나 바이트를 추가·삭제한다
자동 실행변형한 입력을 대상 프로그램에 넣고 반복 실행한다
실행 흐름 관찰이전에 가 보지 못한 코드가 실행됐는지 본다
탐색할 입력 선택새 코드 흐름을 만든 입력을 보관하고 다시 변형한다
이상 결과 저장크래시나 시간 초과를 일으킨 입력을 저장한다

2. 퍼징은 무엇을 오류로 판단할까

2.1 커버리지와 오류 탐지는 역할이 다르다

커버리지 피드백은 "이 입력이 새 부분을 실행했으니 더 탐색해 보자"는 신호이고, 오류 탐지는 "이 입력을 실행했더니 잘못된 동작이 나타났다"는 신호다. 새 코드를 실행했다고 반드시 버그를 찾는 것은 아니다. 반대로 이미 실행해 본 코드도 입력값이 달라지면 버그가 날 수 있다. 커버리지가 높다는 사실만으로 프로그램이 안전하다고 결론 낼 수 없다.

2.2 프로그램이 죽지 않으면 버그를 놓칠 수 있다

버퍼 범위를 조금 넘어 접근해도 프로그램이 바로 종료되지 않는다. 주변 메모리를 건드린 채 계속 실행되다가 나중에 문제가 드러나기도 한다. 그래서 퍼징에는 AddressSanitizer(ASan) 같은 오류 탐지기를 함께 쓴다. ASan은 버퍼 범위 밖 접근, 해제한 메모리 사용, 이중 해제, 잘못된 메모리 해제를 잡아낸다.

도구역할
퍼저입력을 만들고 실행을 반복한다
커버리지 계측어떤 코드가 실행됐는지 관측한다
ASan실행 중 메모리 오류를 탐지한다
디버거오류가 난 상태와 원인을 분석한다

ASan 자체는 입력을 만드는 퍼저가 아니다.

2.3 메모리 오류 말고 다른 문제도 찾을 수 있을까

가능하지만 무엇을 잘못된 동작으로 볼지 먼저 정의해야 한다. 이 판정 기준이나 장치를 테스트 오라클(test oracle)이라고 한다.

  • 프로그램이 비정상 종료하면 실패로 본다.
  • 정해진 시간 안에 끝나지 않으면 조사 대상으로 기록한다.
  • ASan이 메모리 오류를 보고하면 실패로 본다.
  • 반드시 지켜야 하는 조건이 깨지면 실패로 본다.

무손실 인코더와 디코더라면 "인코딩 후 디코딩한 결과는 원본과 같아야 한다"를 검사할 수 있다. 접근 제어라면 "권한 없는 사용자에게 데이터가 반환되면 실패"를 검사할 수 있다. 크래시가 나지 않는 논리 오류도 판정 기준을 설계하면 퍼징으로 찾을 수 있다.

3. 퍼징의 종류

퍼징은 하나의 기준으로만 나뉘지 않는다. 내부 정보를 얼마나 활용하는지가 한 축이고, 입력을 어떻게 만드는지가 다른 축이다.

구분탐색에 쓰는 정보대표 예
블랙박스외부에서 보이는 동작만 본다. 응답이 오는지, 프로세스가 종료됐는지, 연결이 끊겼는지, 응답이 지나치게 느린지네트워크 서비스에 잘못된 요청을 보내 보기
그레이박스커버리지 같은 내부 실행 정보로 다음 입력을 고른다AFL++, libFuzzer
화이트박스프로그램의 조건을 분석해 입력 생성에 쓴다심볼릭 실행, 제약 조건 풀이

3.1 화이트박스가 하는 일

if (x * 3 + 7 == 1000) {
    interesting_function();
}

조건을 분석하면 x = 331을 구할 수 있다. 특정 경로에 도달하는 조건을 모아 그 조건을 만족하는 입력을 만드는 방식이다. 다만 실제 프로그램은 경로와 조건이 많아서 분석 비용이 급격히 커질 수 있다.

3.2 자주 하는 오해

"소스 코드가 없으면 무조건 블랙박스 퍼징이다"는 정확하지 않다. 소스가 없는 실행 파일도 동적 계측으로 커버리지를 모을 수 있다. AFL++의 QEMU·FRIDA 방식이나 Jackalope의 TinyInst가 이런 바이너리 계측에 해당한다. 소스가 없어도 바이너리 계측으로 커버리지를 얻어 입력을 고른다면, 탐색에 쓰는 정보를 기준으로 그레이박스라고 설명할 수 있다.

3.3 변이 기반과 생성 기반

블랙박스·그레이박스·화이트박스와는 다른 분류 기준이다. 변이 기반은 정상 파일의 필드를 바꾸거나 데이터를 덧붙이는 식으로 기존 입력을 바꾼다. 생성 기반은 규칙이나 모델로 새 입력을 만든다. LAB 헤더, 길이 필드, 데이터를 정해진 구조대로 조립하는 식이다. 문법을 이용해 구조를 만족하는 입력을 만드는 문법 기반 퍼징이 대표적이다.

둘을 섞을 수도 있다. 데이터를 4바이트에서 8바이트로 늘릴 때 길이 필드도 8로 함께 고치면, 기존 입력을 변형하면서 구조를 유지한다. 이런 구조 인지적(structure-aware) 퍼징은 형식 검사를 통과해 내부 기능을 더 깊게 검사하는 데 도움이 된다.

4. 퍼저는 무엇이 다른가

4.1 하네스부터 이해하기

퍼저가 만든 입력을 검사할 함수에 전달하려면 연결 코드가 필요하다. 이를 퍼징 하네스(harness)라고 한다. 앞의 예제라면 개념적으로 다음과 같다.

int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size)
{
    parse_record(data, size);
    return 0;
}

퍼징 엔진이 만든 바이트 배열이 parse_record()로 들어간다. 좋은 하네스는 검사할 기능에 실제로 도달해야 하고, 필요한 초기화를 해야 하며, 이전 실행의 상태가 다음 실행을 방해하지 않게 해야 한다. 하네스를 잘못 만들면 실제 프로그램에서는 일어나지 않는 오류를 찾거나, 정작 검사하려는 함수에 닿지 못할 수 있다.

4.2 AFL++

커버리지 피드백으로 입력을 변형하고 탐색하는 과정을 공부하기 좋은 대표 퍼저다. 흐름은 계측용 컴파일러로 빌드하고, 입력 폴더에 초기 시드를 준비하고, 퍼저를 돌려 변형·실행·피드백 수집을 반복하고, 크래시를 일으킨 입력을 확보하는 순서다. 소스 기반 계측뿐 아니라 바이너리 대상 계측 방식도 제공한다.

4.3 Jackalope

바이너리 계측과 대상에 맞춘 커스터마이징을 중심으로 이해하면 된다. 기본으로 TinyInst를 이용한 계측, 입력 변형, 파일이나 공유 메모리를 통한 입력 전달을 제공하고, 변이기와 전달 방식은 대상에 맞게 바꿀 수 있다. 공식 README에는 Windows, macOS, Linux, Android 지원이 적혀 있다. AFL++도 바이너리를 검사할 수 있으므로 두 도구를 "소스용"과 "바이너리용"으로만 나누면 안 된다.

4.4 libFuzzer

같은 프로세스 안에서 특정 함수를 반복 호출하는 커버리지 기반 퍼징 엔진이다. 파일 파서, 압축 처리, 문자열 처리처럼 라이브러리 기능을 좁혀 검사할 때 알맞다. 앞에서 본 LLVMFuzzerTestOneInput()을 진입점으로 연결해 쓴다. 다만 반복 실행 사이에 전역 상태가 남거나 스레드가 계속 돌면 결과가 불안정해질 수 있다.

4.5 boofuzz

프로토콜 메시지의 구조와 통신 순서를 중심으로 검사하는 도구다. 어떤 서버는 사용자 이름 전달, 비밀번호 전달, 기능 실행 명령 전달 순서로 요청해야 특정 기능에 닿는다. boofuzz에서는 메시지 구조와 연결 관계를 정의해 이런 대화를 구성한다. 입력값뿐 아니라 어떤 상태에서 어떤 메시지를 보내는지가 중요한 대상과 연결해 이해하면 된다.

4.6 syzkaller

커널을 대상으로 하는 커버리지 기반 퍼저다. 시스템 호출의 인자와 호출 순서가 입력이 된다. 자원을 만들고, 조작하고, 다른 호출에서 쓰고, 해제하는 과정의 조합을 검사한다. 시스템 호출 설명을 바탕으로 입력을 만들고 VM 안에서 실행해 결과와 커버리지를 수집한다. 그래서 커널 퍼징은 사용자 프로그램의 파일 퍼징과 입력 모델부터 실행 환경까지 다르다.

5. 크래시를 찾으면 취약점을 찾은 것일까

크래시를 찾았을 때 먼저 말할 수 있는 것은 "이 입력을 이 조건에서 실행하니 오류가 났다"까지다. 취약점이라고 부르려면 분석이 더 필요하다.

  1. 재현한다. 같은 입력을 다시 실행해 같은 문제가 나타나는지 본다. 버전, 빌드 옵션, 실행 인자, 초기 상태도 함께 기록한다.
  2. 입력을 줄인다. 원인과 관계없는 부분을 지우면서 같은 실패가 유지되는지 확인한다. 입력이 작을수록 핵심 조건을 이해하기 쉽다.
  3. 근본 원인을 찾는다. 앞의 예라면 입력의 길이 필드를 복사 길이로 쓰면서 목적지 버퍼 크기를 검사하지 않은 것이 원인이다. memcpy()에서 죽었다는 것은 현상이고, 잘못된 길이가 왜 그 지점까지 전달됐는지가 원인 분석이다.
  4. 실제 사용 경로에서 도달할 수 있는지 확인한다. 하네스에서는 터져도 실제 프로그램에는 앞단 검사가 있을 수 있다. 반대로 외부 입력이 그대로 들어올 수도 있다.
  5. 영향을 판단한다. 서비스 중단, 정보 노출, 데이터 변조, 권한 침해 중 무엇으로 이어질 수 있는지 근거를 모은다.
  6. 수정 후 다시 검사한다. 기존 입력으로 문제가 사라졌는지 확인하고, 그 입력을 회귀 테스트로 남긴다.

덧붙임 1: 직접 돌려 보는 최소 흐름

아래는 앞의 예제를 두 가지 방식으로 퍼징하는 최소 명령이다. 학습용 정리이고, 이 명령으로 새 취약점을 찾았다는 뜻은 아니다. 옵션은 설치한 버전의 문서와 함께 확인해야 한다.

AFL++ (파일을 읽는 실행 파일일 때)

# 1) 계측 + ASan으로 빌드
AFL_USE_ASAN=1 afl-clang-fast -g -O1 lab.c -o lab_afl

# 2) 시드 준비 (정상 입력 하나면 시작할 수 있다)
mkdir in && printf 'LAB\x04ABCD' > in/seed

# 3) 실행. @@ 자리에 변형된 입력 파일 경로가 들어간다
afl-fuzz -i in -o out -- ./lab_afl @@

# 4) 크래시는 out/default/crashes/ 에 저장된다

ASan으로 빌드한 대상은 메모리를 많이 쓰므로 AFL++ 문서의 ASan 관련 주의 사항을 먼저 읽는 편이 좋다.

libFuzzer (함수를 직접 호출할 때)

clang -g -O1 -fsanitize=fuzzer,address harness.c -o harness_fuzz
mkdir corpus
./harness_fuzz corpus/

harness.c에는 parse_record()와 앞에서 본 LLVMFuzzerTestOneInput()이 들어가고, main()은 libFuzzer가 제공한다.

덧붙임 2: 퍼징 효율을 올리는 요소

  • 시드의 질. 대상 형식에 맞는 작은 정상 샘플을 여러 개 주는 편이 낫다. 시드가 크면 실행이 느려지고, 형식이 맞지 않으면 파서 안쪽에 닿기 어렵다.
  • 코퍼스 최소화. AFL++는 afl-cmin으로 같은 커버리지를 내는 입력을 줄이고, afl-tmin으로 개별 입력을 작게 줄이는 도구를 제공한다. 5장의 "입력을 줄인다"에 그대로 쓸 수 있다.
  • 사전(dictionary). LAB 같은 매직 값이나 프로토콜 키워드를 사전 파일로 주면 변이가 그 토큰을 직접 끼워 넣는다. AFL++는 -x 옵션으로 사전을 받는다.
  • 지속 모드(persistent mode). 프로세스를 매번 새로 띄우지 않고 한 프로세스에서 여러 입력을 처리해 속도를 크게 올린다. libFuzzer가 같은 프로세스에서 반복 호출하는 방식과 같은 발상이다. 대신 상태가 남지 않게 하네스를 설계해야 한다.
  • 체크섬·압축·암호화된 입력. 변이로 바이트를 바꾸면 체크섬이 틀려 첫 검사에서 막힌다. 이런 대상은 검사를 우회하는 하네스를 만들거나, 변이 뒤에 체크섬을 다시 계산하는 커스텀 변이기를 둔다.

덧붙임 3: ASan 말고도 있는 새니타이저

이름찾는 문제
AddressSanitizer (ASan)버퍼 오버플로, use-after-free, double free 같은 메모리 오류
UndefinedBehaviorSanitizer (UBSan)부호 있는 정수 오버플로, 잘못된 시프트, null 포인터 역참조 같은 정의되지 않은 동작
MemorySanitizer (MSan)초기화하지 않은 메모리 읽기
ThreadSanitizer (TSan)데이터 레이스

새니타이저를 전부 한 빌드에 켤 수는 없다. ASan과 MSan, ASan과 TSan은 같이 쓰지 못하므로 빌드를 나눠 돌려야 한다.

덧붙임 4: 퍼징의 한계와 버그바운티에서의 쓰임

  • 퍼징은 "버그가 없다"를 증명하지 못한다. 시간 안에 닿지 못한 코드는 검사되지 않은 채 남는다.
  • 하네스와 오라클이 검사 범위를 정한다. 하네스가 닿지 않는 기능과 오라클이 정의하지 않은 오류는 못 찾는다.
  • 같은 원인의 크래시가 수십 개 나올 수 있다. 스택 트레이스의 맨 위 함수 등으로 묶어 원인 단위로 정리해야 한다.
  • 버그바운티에서는 크래시만으로 보고하기보다 5장의 순서대로 재현 절차, 최소화한 입력, 근본 원인, 실제 도달 가능성, 영향을 갖춰야 한다. 퍼징은 허가된 범위의 대상에서만 돌려야 한다.

정리

퍼저는 입력을 만들고 반복 실행하는 도구일 뿐이고, 무엇을 버그로 볼지는 오라클과 새니타이저가 정한다. 어디에 넣을지는 하네스가 정한다. 퍼저마다 다른 점은 결국 대상(프로그램, 함수, 프로토콜, 커널), 입력의 구조, 계측 방식이다. 크래시를 찾은 뒤에는 재현, 최소화, 원인 분석, 도달 가능성, 영향 판단, 수정 검증까지 가야 취약점 보고가 된다.
